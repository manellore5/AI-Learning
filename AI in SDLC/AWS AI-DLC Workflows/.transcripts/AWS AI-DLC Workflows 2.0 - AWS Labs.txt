# AI-DLC Workflows

Announcing 2.0 (GA). AI-DLC Workflows 2.0 is now generally available. The new version makes autonomous software development practical by turning AI agents into verifiable, self-correcting engineering workflows — one harness-neutral core, rendered natively across Claude Code, Kiro IDE, Kiro CLI, Codex CLI, and opencode.

A native implementation of the AI-DLC methodology (AI-Driven Development Life Cycle) that runs on many harnesses from one source of truth. Run a full software-development lifecycle with a 14-agent roster — 11 domain experts, 2 review-only agents, and the adaptive-workflows composer — working through a 32-stage workflow, with you approving every gate. The methodology lives once, in a harness-neutral core/; each harness adds a thin surface that decides how it shows up. Edit the methodology in one place; every harness distribution is generated from it.

Why AI-DLC: "Ad-hoc AI coding works until the project gets real. Then context drifts between prompts, the reasoning behind a decision goes unrecorded, and the model quietly does something you never asked for." AI-DLC puts structure around the work: each stage has a clear owner, every decision passes an approval gate before the next starts, and it records what it learns from corrections. The same engine runs a throwaway PoC and a regulated enterprise rollout — it just runs more stages, in more depth.

Key Features:
- 5 phases, 32 stages — Initialization, Ideation, Inception, Construction, Operation
- 14-agent roster — 11 domain experts, 2 quality-gate reviewers, adaptive-workflows composer
- 9 adaptive scopes (enterprise through workshop) with auto-detection; adaptive composer (/aidlc compose)
- 3 depth levels (Minimal/Standard/Comprehensive)
- 3 test strategy levels (Minimal/Standard/Comprehensive) — independent of depth
- CLI utilities — jump to any stage/phase, check status, change scope/depth/test strategy mid-workflow
- Approval gates at every stage
- Two-tier knowledge system — methodology knowledge ships; team knowledge user-managed
- Rules and a learning loop — human corrections become persistent behavioral rules
- 74-event audit trail
- Session resume — checkpoint, redo, jump to stage, or start fresh

Methodology and Implementation: AI-DLC is a methodology defined by AWS. This repository is its native, multi-harness implementation — methodology rendered as skills, agents, hooks, and tools from one harness-neutral core/, running inside Claude Code, Kiro IDE, Kiro CLI, Codex CLI, opencode, or any capable harness you port it to.

Pick Your Harness (Install / Invoke):
- Kiro IDE: dist/kiro-ide/.kiro/ + dist/kiro-ide/aidlc/ → <project>/ (+ AGENTS.md); invoke /aidlc
- Kiro CLI (>=2.6): dist/kiro/.kiro/ + dist/kiro/aidlc/ (+ AGENTS.md); invoke /aidlc
- Claude Code: dist/claude/.claude/ + dist/claude/aidlc/; invoke /aidlc
- Codex CLI (>=0.145.0): dist/codex/ (.codex/ + .agents/ + aidlc/ + AGENTS.md); invoke $aidlc (or /skills → aidlc)
- opencode (>=1.17): dist/opencode/ (.aidlc/ + .opencode/ + aidlc/ + opencode.json + AGENTS.md); invoke /aidlc

The deterministic engine — state machine, audit log, referee that coordinates parallel agents — is byte-identical across every harness; only the shell differs. AI-DLC on Kiro works best with Claude Opus 4.8 (paid Kiro plan). Recommended model: Claude Opus 4.8.

Quick Start prerequisites (every harness): install bun (curl -fsSL https://bun.sh/install | bash). bun must be on the non-interactive PATH (~/.zshenv / ~/.bashrc), not just ~/.zshrc. Every harness runs on AWS Bedrock — enable model access and provide AWS credentials. Get the code: git clone https://github.com/awslabs/aidlc-workflows.git; cd aidlc-workflows; git checkout v2. The aidlc/ shell ships the pre-built aidlc/spaces/default/memory/ method tree; /aidlc --doctor fails "workspace shell ready" without it. Verify with /aidlc --doctor, start with /aidlc <description>.

Documentation: User Guide (building software with AI-DLC), Harness Engineer Guide (shaping behavior — stages, agents, scopes, rules, sensors, team knowledge), Developer Reference (changing AI-DLC itself — architecture, orchestrator, stage protocol, hooks, state machine, testing).

Repository Layout (3 zones): core/ (hand-authored source of truth — 25 aidlc-*.ts tools, stage protocol + 32 stage files + conductor, 14 agents, knowledge/memory/scopes/sensors/hooks, 3 skills, templates); harness/ (thin per-harness authored surfaces: claude, kiro-ide, kiro, codex); plugins/ (optional owned plugins + additive contribution seam; test-pro reference); scripts/package.ts (the build entry; --check = drift guard for CI); dist/ (GENERATED, COMMITTED, DRIFT-GUARDED — never hand-edit); tests/ (all-TypeScript); docs/. Only core/ and harness/ are edited; bun scripts/package.ts regenerates dist/.

Build/Regenerate: bun scripts/package.ts [<name>] [--check]; bun scripts/build-binaries.ts [--all-targets].
Testing: bun tests/run-tests.ts [--ci|--release]; bash tests/run-tests.sh --ci.
References: AWS AI-DLC Blog Post; AI-DLC Method Definition Paper; AI-DLC Workflows 2.0 Specification (AWS Labs whitepaper).

SOURCE 2 — AI-DLC Workflows 2.0 Roadmap
========================================================================

North star reference — seven functional goals:
1. Mimic what we practice in the real world — a stage executed by a configurable ensemble (Owner, Collaborator, Verifier) with consistent semantics across harnesses.
2. Customization of behaviour — encode new behaviours/policies/constraints in no more than two targeted changes, reusable across harnesses.
3. Adaptiveness of workflows — scale in (report triage to compact Fix, Test, PR) and scale out (decide next stages at boundaries); composition not hard-wired.
4. Verifier as a true adversary — adversarial quality gate; may use a different LLM than the producer; validates against machine-checkable evidence; budgeted self-heal loop escalating to HITL.
5. Support for cyclic, directional flows — forward progression plus governed, directional feedback loops.
6. Preserve artefact traceability — downstream stages enrich upstream artefacts rather than spawning disconnected ones.
7. Organizational, not project-local, artefact repository — shared org knowledge layer across projects, intents, and repos.

Goal scorecard:
1 Real-world ensemble — Partial (2.0.x roles + 2.1.8 reviewer wiring) → 2.5.0
2 Customization — Shipped (2.0.x rules stack + 2.3.0 plugins) → plugin deferred surfaces, stage rules layer
3 Adaptiveness — Shipped (2.2.0 composer + scale-in) → (boundary auto-assessment deliberately human-initiated)
4 Verifier as adversary — Partial (2.0.x reviewer loop, 2.3.1 model split) → 2.4.0
5 Cyclic flows — Partial (within-stage review loop, HITL hardening) → 2.6.0
6 Traceability — Partial (artefact graph + upstream-coverage sensor) → 2.7.0
7 Org repository — Shipped (2.1.0 spaces/intents/org-KB) → done
