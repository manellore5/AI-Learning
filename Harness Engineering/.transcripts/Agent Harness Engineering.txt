# Agent Harness Engineering
A coding agent is the model plus everything you build around it. Harness engineering treats that scaffolding as a real artifact, and it tightens every time the agent slips. Roughly: anytime an agent makes a mistake, you engineer a solution so the agent never makes that mistake again.

We've spent two years arguing about models. But the model is one input into a running agent. The rest is the harness: prompts, tools, context policies, hooks, sandboxes, subagents, feedback loops, recovery paths wrapped around the model so it can finish something. A decent model with a great harness beats a great model with a bad harness.

Viv Trivedy coined "harness engineering" ("Anatomy of an Agent Harness"). Dex Horthy tracks the pattern. HumanLayer frames most agent failures as "skill issues" (configuration, not model weights). Anthropic's engineering team published a breakdown of designing a harness for long-running work. Birgitta Böckeler has a user-side overview.

## What is a harness, really?
Viv: "Agent = Model + Harness. If you're not the model, you're the harness." A raw model is not an agent; it becomes one once a harness gives it state, tool execution, feedback loops, enforceable constraints. Concretely a harness includes: system prompts, CLAUDE.md, AGENTS.md, skill files, subagent prompts; tools, skills, MCP servers and their descriptions; bundled infrastructure (filesystem, sandbox, browser); orchestration (subagent spawning, handoffs, model routing); hooks and middleware for deterministic execution (compaction, continuation, lint checks); observability (logs, traces, cost/latency metering).
Simon Willison: an agent "runs tools in a loop to achieve a goal." Claude Code, Cursor, Codex, Aider, Cline are all harnesses; the model underneath is sometimes the same, but behaviour is dominated by the harness. coding agent = AI model(s) + harness. Most of the leverage sits on the right-hand side.

## The "skill issue" reframe
The agent does something dumb, the engineer blames the model, filed under "wait for next version." Harness engineering rejects that. Failures are legible: unknown convention -> add to AGENTS.md; ran a destructive command -> add a blocking hook; lost in a 40-step task -> split into planner + executor; kept "finishing" broken code -> wire a typecheck back-pressure signal into the loop. HumanLayer: "it's not a model problem. It's a configuration problem."
Data point (Viv + HumanLayer): on Terminal Bench 2.0, Claude Opus 4.6 in Claude Code scores far lower than the same model in a custom harness. Viv's team moved a coding agent Top 30 -> Top 5 by changing only the harness. Models get post-training coupled to the harness they were trained against; moving them into a better harness unlocks capability the original left on the floor. The gap between what models can do and what you see is largely a harness gap.

## The ratchet: every mistake becomes a rule
Treat mistakes as permanent signal. E.g. agent ships a PR with a commented-out test: next AGENTS.md says "never comment out tests; delete or fix them"; next pre-commit hook greps for .skip( and xit( in the diff; next reviewer subagent flags commented-out tests as a blocker. Add constraints only when you've seen a real failure; remove them only when a capable model made them redundant. Every line in a good AGENTS.md traces to a specific failure. Harness engineering is a discipline, not a framework — shaped by your failure history; you can't download it.

## Working backwards from behaviour
Viv's pattern: behaviour we want (or want to fix) -> harness design to help the model achieve this. Mapping: work with real data durably -> filesystem + git; write and execute code -> bash + code execution; safe execution + defaults -> sandboxed environments + tooling; remembering new knowledge -> memory files, web search, MCPs; performance over long contexts -> compaction, tool offloading, skills; long-horizon work -> Ralph loops, planning, verification. If you can't name the behaviour a component delivers, it shouldn't be there.

### Filesystem and Git: durable state
Most foundational primitive, underrated because boring. Models operate only on what fits in context; without a filesystem you're copy-pasting. Filesystem gives a workspace to read data/code/docs, offload intermediate work, and coordinate across agents/humans via shared files. Git adds versioning for free — track progress, roll back, branch experiments. Most other primitives point at the filesystem.

### Bash and code execution: the general-purpose tool
Main loop is ReAct: reason, act via tool call, observe, repeat. A harness only executes tools it has logic for. Either pre-build a tool for every action or give the agent bash to build tools on the fly. Willison: agents excel at shell; most tasks collapse to a few CLI invocations. Bash + code execution is the default general-purpose strategy. Teaching a single gadget vs handing them a kitchen.

### Sandboxes and default tooling
Bash must run somewhere safe; local execution is risky and doesn't scale to parallel agents. Sandboxes give isolated environments — run code, inspect files, install deps, verify work; allow-list commands, enforce network isolation, spin up/tear down on demand. Good defaults: pre-installed runtimes/packages, Git and test CLIs, headless browser. Browsers, logs, screenshots, test runners let the agent observe its own work and close the self-verification loop. The model doesn't configure its execution environment — that's a harness-level call.

### Memory and search: continual learning
Models have no knowledge beyond weights + current context; without editing weights, add knowledge via context injection. Harnesses support memory file standards like AGENTS.md injected every start; as the agent edits it, the harness reloads it, carrying knowledge across sessions — crude but effective continual learning. Web search and MCP tools like Context7 bridge the training cutoff.

### Battling context rot
Context rot: models get worse as the window fills. Three techniques: Compaction (summarize/offload older context near full; letting the API error isn't an option); Tool-call offloading (keep head/tail tokens above a threshold, offload full output — e.g. 2,000-line logs — to filesystem for on-demand read); Skills with progressive disclosure (reveal instructions/tools only when needed; loading everything at startup degrades performance). Anthropic adds full context resets: tear the session down and rebuild from a compact hand-off file — compaction alone wasn't sufficient for long tasks.

### Long-horizon execution: Ralph Loops, planning, verification
Models suffer early stopping, poor decomposition, incoherence across context windows. Ralph Loop: a hook intercepts the model's attempt to exit and re-injects the original prompt into a fresh context window, forcing continuation against a completion goal; each iteration starts clean but reads prior state via the filesystem. Planning: model decomposes a goal into steps in a plan file; harness supports with prompting/reminders; after each step self-verification hooks run a test suite and loop failures back with error text. Planner/generator/evaluator splits: Anthropic finds separating generation from evaluation beats self-evaluation (agents skew positive grading themselves; "GANs for prose"). Sprint contract: generator and evaluator negotiate what "done" means before code is written.

### Hooks: the enforcement layer
Hooks separate "I told the agent to do X" from "the system enforces X." A hook runs at a lifecycle point (before tool call, after file edit, before commit, on session start): run typecheck/lint/tests after edits and surface failures; block destructive bash (rm -rf, git push --force, DROP TABLE); require approval before PR/push to main; auto-format on write. Principle: success is silent, failures are verbose — passing typecheck says nothing; failing injects error text into the loop for self-correction. Feedback loop is almost free in the common case, directly actionable on failure.

### AGENTS.md and tool choice
The flat markdown rulebook at repo root is the single highest-leverage config — it lands in the system prompt every turn. Conventions: package manager, test framework, formatting, "never touch /legacy", "always use our logger". Lessons: keep it short (HumanLayer under 60 lines — pilot's checklist, not style guide); earn each line (trace to a past failure or hard constraint; ratchet, don't brainstorm). Same for tools: each tool's name/description/schema is stamped into the prompt every request; ten focused tools beat fifty overlapping. Security: tool descriptions are trusted text the model reads; a sloppy/malicious MCP can prompt-inject the agent.

### What this looks like in production
Fareed Khan's (estimated) breakdown of Claude Code's architecture: input layer (UI, session manager, permission gate); knowledge layer (skill registry, context compressor, task graph, memory store); integration layer (MCP runtime, external servers); execution layer (tool dispatch, streaming runtime, prompt cache); output layer; observability layer (event bus, background executor); multi-agent layer (subagent spawning, teammate mailboxes, FSM protocol, autonomous board, worktree isolator). Master agent loop at the centre. Context injection = knowledge layer; loop state = memory store + worktree isolator; destructive-action hooks = permission gate; subagent firewalls = multi-agent layer; tool dispatch = where MCP + bash plug in. Claude Code's trajectory is about the harness at least as much as the model.

## Harnesses don't shrink, they move
As models improve, the space of interesting harness combinations doesn't shrink — it moves. Naive story: better models make harnesses obsolete (model can plan -> no planner; coherent long-horizon -> no context resets). Opus 4.6 largely killed context-anxiety (Sonnet 4.5 wrapped up prematurely near its perceived limit), making a class of anxiety scaffolding dead code. But the ceiling moved: newly reachable tasks have their own failure modes needing multi-day memory policy, three-agent coordination, evaluators for UI design quality. Anthropic: "every component in a harness encodes an assumption about what the model can't do on its own" — when the model improves, that component becomes load-bearing for nothing and should come out; new unlocks need new scaffolding.

### The model-harness training loop
A useful primitive is discovered in the harness -> standardized into the product -> used when training the next model -> the next model improves at that primitive -> repeat. Today's agent products are post-trained with harnesses in the loop; models get better at filesystem ops, bash, planning, subagent dispatch. Why Opus 4.6 feels different in Claude Code vs another harness, and why changing a tool's logic causes strange regressions (co-training creates overfitting: apply_patch vs str_replace). Implications: a harness is a living system, not a one-time config; the best harness is the one designed for your task, not necessarily the one the model trained inside. Viv's Top 30 -> Top 5 jump is the proof point.

## Harness-as-a-Service
Viv's HaaS framing: moving from building on LLM APIs (return a completion) to harness APIs (return a runtime) — Claude Agent SDK, Codex SDK, OpenAI Agents SDK. You get the loop, tools, context management, hooks, sandbox out of the box and customize along four pillars (system prompt, tools, context, subagents). Old default path: build your own loop, tool-calling, conversation state, approval flow. New default: pick a harness framework, configure the four pillars, focus effort on domain-specific prompt/tool design. That's what makes "skill issue" tractable — tuning a well-factored config surface, not rebuilding an agent. Viv: "good agent building is an exercise in iteration. You can't do iterations if you don't have a v0.1."

## Where this is going
Top coding agents (Claude Code, Cursor, Codex, Aider, Cline) look more like each other than their underlying models do — harness patterns are converging on the load-bearing scaffolding that turns a generative model into something that can ship. Open problems (Viv): orchestrating many agents in parallel on a shared codebase; agents that analyze their own traces to identify and fix harness-level failure modes; harnesses that dynamically assemble the right tools and context just-in-time instead of being pre-configured at startup — where harnesses stop being static config and start becoming closer to a compiler.
